# Charts use d3-scale as a peer dep; no d3-selection or d3-shape

SUI's chart family adds `d3-scale` as a peer dependency (~3kb gz). It's pure math with no DOM dependency — used by `scales.ts` for `scaleTime` and downstream tick formatting. We explicitly **exclude `d3-selection`** because Solid owns rendering; d3-selection's imperative DOM mutation conflicts with Solid's reactive render model. We also **exclude `d3-shape`** in v1: the closed `Shape` enum (`'circle' | 'chevron' | 'pin' | { path; viewBox? }`) is small enough to hand-author, and the custom-path descriptor is an escape hatch for the long tail. Slots receive scales + descriptors from `useChart()` and emit JSX. Pattern matches `DagChart`'s existing `d3-dag` peer dep.

We chose this because (a) Solid's render model is the source of truth for the DOM — interleaving d3-selection would create two competing owners of each element, (b) `d3-scale` is stateless and trivially testable against the existing `Scale` interface, and (c) inline shape paths keep the peer-dep surface minimal so consumers don't install kilobytes they never use.

The accepted cost is that contributors must internalize the split: **d3 = math only; Solid = render.** This is documented in CONTEXT.md's glossary additions ("Slot (chart)", "Descriptor (visual)"). If a future slot genuinely needs `d3.line`/`d3.area`/`d3.symbol`, that change re-introduces `d3-shape` as a peer dep — the precedent here (admit pure-math d3 modules, exclude d3-selection) makes that path easy. Reversing the d3-selection decision would require `createEffect` plumbing to coordinate Solid and d3 ownership; not worth it for the surface we have.
